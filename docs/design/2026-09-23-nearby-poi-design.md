# 附近地點(生活機能)設計

日期：2026-09-23
狀態：公車（第 0 階段）、我的地點、生活機能（第 1、2 階段）、垃圾車、嫌惡設施、YouBike、災害潛勢已實作；見各節的「已實作」註記

## 需求

點地圖上某個點（房源標記，或地圖任意位置）→ 看到附近有什麼：餐飲、超商 / 超市 / 賣場、醫院 / 診所 / 藥局、公園、警察局、廟宇、學校、市場、郵局 / 銀行、健身房…。
延伸：**我的地點**（公司、爸媽家、常去的健身房）→ 每間房源顯示到這些地點的距離 / 通勤時間，可拿來篩選與比較。

## 餐飲要特別處理（使用者強調餐廳很重要）

OSM 的餐飲只有七八成，小店常缺，所以餐飲用三層疊起來：

| 層 | 來源 | 有什麼 | 成本 |
|---|---|---|---|
| 1. 基底 | OSM（同上） | 約 2 萬筆連鎖與熱門店，名稱、類型、部分營業時間 | 免費，一次下載 |
| 2. 精準 | **menmap 的拉麵店資料**（`menmap.shunzz.com/shops.json`，1,426 家，含 Google 評分、營業狀態、價位，每天更新） | 直接畫上地圖，點了可跳去麵咩撲 | 免費，現成 |
| 3. 完整 | **Google Maps 連結**：「在 Google Maps 看這附近的餐廳」，帶座標開 `https://www.google.com/maps/search/餐廳/@lat,lng,17z` | 全量、有評論，但不存資料 | 免費，零維護 |

之後若想要「收藏的房源附近有哪些餐廳、評分多少」存下來：只對收藏的房源（幾十間）用 menmap 的 `ramen` 採集後端搜 Google Maps「餐廳」關鍵字抓前 20 筆，資料量小、住宅 IP 抓得到。全雙北抓 Google Maps 不做（量太大、Google 條款不准存）。

面板的「餐飲」一列顯示：OSM 數量 + 拉麵店數量（有評分的用星號標）+ Google Maps 按鈕。

## 公車：重點是「住這裡可以搭哪幾路」

> **2026-09-24 已實作（第 0 階段 + 我的地點的最小版）**，和下面原始設計的差異：
> - 資料表改成 `bus_routes`（一條「路線 × 方向」一列，含簡化後的線形與班表）+ `bus_route_stops`（路線方向上的每一站，帶沿線累計距離與從起點算的分鐘）。附近查詢直接 bbox 查 `bus_route_stops`，不另建站牌表。
> - API 是 `GET /api/bus/nearby`（帶 `to_lat/to_lng` 就多算「直達目的地」）與 `GET /api/bus/routes/:key`；匯入是 `POST /api/ingest/bus/{routes,stops,commit}`，覆蓋式、有「新版不到一半就擋」的保護。
> - 班表：TDX `Schedule` 的 Timetables（逐班發車）與 Frequencys（班距區間）都收；經過某站的時刻 = 起點發車 + 起點到該站分鐘（時刻表有就用，沒有用距離 ÷ 14 km/h 估），介面都標「預估」。
> - 通勤：`my_places` 表 + `/api/places`；頂欄「我的地點」或公車區塊的「輸入公司地址」開對話框：輸入地址 → 瀏覽器直接問 Nominatim（由細到粗：完整 → 到號 → 到巷 → 到路，`src/shared/address.ts`）→ 小地圖拖曳圖釘對到門口 → 存。沒設地點前通勤區塊只顯示這個入口（2026-09-26 取代原本的地圖右鍵，右鍵不直覺）。面板選「通勤到 公司」→ 列出直達路線，依「走路 + 等車（尖峰班距一半）+ 坐車 + 走路」排序，點了在地圖畫上下車那段。
> - 採集：`npm run collect -- bus`（`collector/bus/`），原始 JSON 快取在 `data/tdx/`。
> - **所有房源一次算（2026-09-29）**：`GET /api/commute` 回「每間房 × 每個我的地點」的最佳直達。做法是對每個地點先找 500m 內到得了的路線方向，撈這些路線在下車站之前的站丟進網格，房源只看附近格子——查詢數只跟地點數有關，跟房源數無關。列表每張卡片列出到每個地點的時間、可依通勤排序（多個地點：先比幾個地點沒直達，再比最久的那個）；篩選列「通勤 ≤ N 分」地圖與列表共用，多個地點時預設每個都要在上限內，可在展開的篩選裡只勾部分地點。面板的通勤區塊一個地點一行，點開看全部搭法。
> - **轉乘（2026-09-30）**：通勤改成公車 + 捷運、最多轉乘一次（公車直達 / 捷運 / 公車轉公車 / 公車轉捷運 / 捷運轉公車 / 走路），`src/worker/transit/`。做法是從目的地往回標記「在這站上車到目的地要幾分」，最後一段、第一段各算一次，房源只要看走得到的站（公車 400m、捷運 1km）。捷運圖由 `public/mrt.json` 的站序編號建（支線手動接），站間時間用距離估、換線 +4 分；轉乘 +2 分緩衝；公車網路整份放 Worker 記憶體（以匯入版本為快取鍵）。沒匯入公車時仍算捷運與走路。面板「通勤」獨立成一區（每個地點一行，點開每種搭法，再點看每段並在地圖畫出整趟），公車區塊只剩附近路線。
> - **捷運官方站間時間（2026-09-29）**：`npm run collect -- metro` 從 TDX `Rail/Metro/S2STravelTime`（TRTC、NTMC、TYMC）產生 `public/mrt-times.json`（進 git，Worker 建圖時 import），371 段；原本的距離估算普遍高估 10–18%，換成官方值後 3000 間假房源的通勤平均快 3–4 分。淡海、安坑輕軌 TDX 沒有，仍用距離估；R01–R02 也沒有。
> - **依時段、上下班分開（2026-09-29）**：使用者要評估的是「住這裡平常怎麼通勤」，班次會隨時段變。通勤改成兩組可自訂的時段：上班（預設平日 08:00，住處 → 地點）、下班（預設平日 18:00，地點 → 住處），各自可改日子（平日 / 週六 / 週日）與出發時間，存在篩選設定（localStorage）。
>   - 公車等車 = 出發前 60 分 ~ 後 30 分之間起點發車的平均班距一半（`serviceWait`，shared/bus.ts）；那段時間沒車（當天不開、還沒發、已收班）的路線不算；沒有班表資料的路線（約四成）當等 10 分、視為有開。
>   - 捷運班距分平日尖峰 / 離峰與假日 / 23 點後三級（mrt.ts 的表），00:00–06:00 不營運。
>   - 下班方向：`reverseNet` 把每條路線方向的站序倒過來，同一套「從目的地往回」拿住處當目的地算，行程再翻回正向（`flipTrip`），所以仍是每個地點算一次、跟房源數無關；實測 3000 間 × 2 地點各時段都約 0.7–0.85 秒。
>   - 走路加紅綠燈：沿街每 300m 算一個號誌路口、平均等 0.6 分（`walkMin`）。
>   - 介面：篩選列「上班 / 下班」切換（列表、地圖、排序、通勤上限跟著切），同一列改日子與時間；房源面板每個地點上下班兩行並列，點開可切換看各自的搭法。
> - 不做：即時到站（使用者確認不需要：要的是評估平常的通勤，不是等車）。
> - **路線名稱拆成主路線 + 子路線說明（2026-09-29）**：真實 TDX 的 SubRouteName 是「307莒光往撫遠街」「669狗狗公車」「12返程半」，當顯示名會讓同一路拆成好幾組、也沒辦法用「307」找。`bus_routes.name` 改用 RouteName（主路線名，同名視為同一路：附近路線合一組、轉乘不算同一路、直達只留一條），另加 `variant` 存說明（`routeVariant`：去掉主路線名、結尾「往{終點}」、純方向字）。雙北 2572 個路線方向 → 1051 條主路線，1063 個帶說明。**migration 0006，家裡要 `db:migrate:local` 後重跑一次 `collect -- bus`。**
> - **篩選「經過路線」（2026-09-29）**：篩選列「經過路線」輸入公車主路線名或捷運線名（307、紅30、板南線 / 板南 / BL），任一條走得到就留（公車站 400m、捷運站 800m 內），地圖與列表共用。`GET /api/bus/along?names=` 回房源 id 與每個字對到的路線；公車名比對是「相同，或以它開頭且下一個字不是數字 / 英文字母」，所以 307 會連「307西藏三民」一起算（TDX 把同一路的另一種走法建成另一條路線），但「紅3」不會對到紅30。`GET /api/bus/names` 給輸入框的建議清單。
> - 還沒做：轉乘兩次以上。

使用者要的不是站牌位置，是**路線**：站在這間房，走幾分鐘內有哪些路線可搭。所以路線資料一開始就要進來，站牌只是載體。

### 資料來源：交通部 TDX（免費，要註冊拿 client id / secret）

一次下載雙北全部路線與站牌，放 D1，一個月更新一次：
- `Bus/Stop/City/{Taipei|NewTaipei}`：站牌（StopUID、站名、經緯度）
- `Bus/StopOfRoute/City/{…}`：每條路線的站序（RouteUID、RouteName、方向、站牌清單）
雙北約 1,100 條路線、1.8 萬個站牌、站牌×路線約 5 萬列。

備案（不用金鑰）：data.taipei「公車站牌 / 路線站牌」CSV、data.ntpc.gov.tw 新北公車站牌；格式兩市不同，先用 TDX 一套解決。
OSM 的 `highway=bus_stop` 有站名但路線資料不全，只當備援。

> **生活機能已實作（2026-09-30）**，和下面原始設計的差異：
> - 採集：`npm run collect -- pois [--only=food,park]`（`collector/pois/`）。Overpass 一類一類抓，餐飲切 3×3、公園 / 學校 / 宮廟切 2×2 塊；每次查詢間隔 10 秒、429 / 504 / 逾時退避重試並輪流換 `overpass-api.de` / `overpass.kumi.systems`；原始回應快取 `data/osm/`（30 天內重跑直接用，中斷後從沒抓完的塊繼續）。範圍擴到整個新北（24.67–25.30, 121.28–122.01）。
> - 拉麵另外從 menmap `shops.json` 抓（雙北、營業中，約 500 家，帶 Google 評分與地圖連結）。
> - 類別（`src/shared/poi.ts`）：超商、超市量販、餐飲、拉麵、市場、公園（含遊戲場，不含私人花園）、診所（含牙醫）、藥局、醫院、運動（健身房 / 運動中心 / 游泳池）、洗衣、郵局銀行、學校、宮廟教堂、警察局。`access=private` 的不收。
> - 表 `pois`：主鍵 (category, key)，同一個 OSM 地點可屬於兩類；每類覆蓋式匯入，commit 時新版不到舊版一半就擋（帶 `--force` 才換）。
> - 查詢不走 D1 bbox，整份進 Worker 記憶體網格（同公車網路）：`GET /api/nearby` 每類數量 + 最近 5 個（有名字的優先）；`GET /api/nearby/summary` 每間房源每類數量（比較表用）。沒用 KV。
> - 介面：房源面板「生活機能」（500m / 1km、主要類別常駐、其他收在「更多」，點一類列最近 5 個並在地圖畫點與半徑圈；拉麵顯示評分、連到 Google Maps；附「Google Maps 看附近餐廳」）；比較表「生活機能（走路 500m 內）」每類一列、多的標綠。
> - **垃圾車（2026-09-30）**：`collect -- pois --only=garbage` 抓雙北環保局開放資料（臺北市資料大平臺「垃圾車點位路線資訊」約 4 千點，含抵達 / 離開時間；新北市「垃圾車路線」約 2.6 萬點，含每日一般垃圾 / 回收 / 廚餘旗標）。`pois` 多 `note / minute / days` 欄（migration 0010）；台北市資料沒星期，套全市週三、週日不收。面板「垃圾車」依地點合併午晚兩班的時間。房東有沒有垃圾代收：591 沒這個欄位，用屋況介紹 / 標籤關鍵字判斷（`garbageService`：「垃圾代收」「子母車」「垃圾集中」→ 有；「需自行追垃圾車」→ 沒有；都沒寫 → 不確定）。需求設定可加「走 N 公尺內要有幾點以後、平日至少 3 天的垃圾車」，房東寫了代收就免（`GET /api/garbage/fit` 一次算所有房源）。
> - **嫌惡設施 / 噪音源（2026-09-30）**：加油站、變電所（`minor_distribution` 配電箱與地下 / 室內的不算）、殯葬（`shop=funeral_directors` 與殯儀館；OSM 禮儀社標得很少，雙北只有 46 筆）、垃圾場焚化、墓地、夜市（從市場資料挑名字有「夜市」的）、快速道路（motorway / trunk 高架）、鐵道高架（鐵路、高鐵、捷運）。線狀的兩類只抓非隧道段（地下段沒噪音），每 40m 取一點存成 `w{id}:{i}`；渡線、側線、機廠線（`service=*`）不收。查詢時線狀類別依名稱合併，只留每條路最近那一點。面板「生活機能」下方一列「注意」列最近距離（≤100m 紅、≤300m 黃）；`/api/nearby/summary` 多回 `nearest`（可避開類別的最近距離），比較表「嫌惡設施（最近距離）」、需求設定「不要太近」（50–300m 內不要有勾選的類別，宮廟也可以勾）。
> - **YouBike（2026-09-30）**：雙北 YouBike 2.0 站點（臺北市 tcgbusfs JSON、新北市開放資料），只存站點不看即時車數，進 `pois`（`youbike`）。通勤規劃多三種搭法（`src/worker/transit/bike.ts`、plan.ts）：騎到目的地（5km 內）、騎去捷運站（3km 內，捷運站 150m 內要有站）、捷運下車再騎；騎乘 = 直線 × 1.25 ÷ 12 km/h + 租還 2 分，住處 / 目的地走到站 300m 內。篩選列「含 YouBike」可關（`bike=0`）。3000 間假房源中位數 41 → 38 分，約三分之一最快是騎車接捷運。
> - **災害潛勢（2026-09-30）**：淹水用水利署第四代淹水潛勢圖（雙北），取 6 小時 150mm（短時強降雨）與 24 小時 500mm（颱風）兩個情境、深度 1–5 級；土壤液化用臺北市工務局潛勢圖（低 / 中 / 高；**新北市沒有開放資料**，面板標「沒有資料」而不是「不在潛勢區」）。原始檔是 7z SHP / GeoJSON，由 `scripts/build_hazards.py`（py7zr、pyshp、pyproj；TWD97 → WGS84、簡化 5m、丟掉 200m² 以下碎塊）轉成 `data/hazard/hazards.json`（約 1.5 萬個多邊形、4 MB），`npm run collect -- hazards` 推進 `hazard_zones`（migration 0011，覆蓋式、新版不到一半就擋）。Worker 整份進記憶體網格做點在多邊形判斷：`GET /api/hazards?lat&lng&city`、`GET /api/hazards/summary`（3000 間約 0.2 秒）。面板「災害風險」區塊、比較表一組、需求設定「避開淹水潛勢區（短時強降雨會淹或颱風 0.5m 以上）」「避開土壤液化高潛勢」。
> - **航空噪音防制區(2026-09-30)**:環保局公告是「依里」分級(第一級 Ldn 60–65 dB、第二級 65–75、第三級 75 以上),沒有等噪音線圖資,所以用里界多邊形對上公告的里名:臺北市環保局 CSV(Big5,88 個里:中山、松山、內湖、南港、大同)、新北市環保局公告全文(三重 34 里、汐止 2 里第一級;林口下福里第二級是桃園機場),里界用臺北市 / 新北市民政局的里界 SHP(TWD97 TM2;內政部 TGOS 的全國檔從雲端抓會 403)。`build_hazards.py` 一起轉,存成 `hazard_zones` 的 `airnoise`(不用新 migration)。面板「災害風險」、比較表、需求「避開航空噪音區(第二級以上)」。

## 資料模型

```
bus_stops        stop_uid, name, city, lat, lng            index (lat, lng)
bus_routes       route_uid, name(307|紅30|…), city, kind(一般|幹線|快速|…)
bus_stop_routes  stop_uid, route_uid, direction(0|1)      index (stop_uid)、index (route_uid)
```

### 查詢：`GET /api/nearby/bus?lat=&lng=&radius=400`
1. bbox 篩 `bus_stops`，算距離，留半徑內（預設 400m ≈ 步行 6 分）。
2. JOIN `bus_stop_routes`，彙整成兩種輸出：
   - **路線清單**（主角）：`[{route: "307", nearest_stop: "黎明社教中心", distance_m: 101, walk_min: 2}, …]`，同路線只留最近的站，依距離排序。
   - **站牌清單**：`[{stop, distance_m, routes: ["307","262"]}, …]`。
3. KV 快取 1 天（key 同 POI）。

### 介面
- 面板「公車」區塊：一排路線徽章（`307` `262` `紅30` `藍7`…），每個徽章下小字「黎明社教中心 · 2 分」；徽章數量多就顯示前 12 個加「還有 8 條」。點徽章 → 地圖上高亮那條路線經過的附近站牌（之後再畫整條路線幾何）。
- 站牌本身在地圖上用巴士圖示畫半徑內的。
- 篩選列：「有經過 〔307▾〕 的公車」多選；「我的地點」之後可做「有公車直達公司」（兩點附近路線交集）。
- 591 的「最近公車站」（`positionRound.data[traffic]`）順手存進 `raw_json.traffic` 當備援顯示，但主體是 TDX。

### 之後
- 到站時間（TDX `EstimatedTimeOfArrival`，即時）；路線幾何（TDX `Shape`）畫在地圖上。
- 「有公車直達公司」：房源 400m 內路線 ∩ 公司 400m 內路線，且方向對。

## 資料模型

```
pois            id, osm_id, osm_type(node|way|relation), category(超商|超市|餐飲|…), subtype(原 tag 值), name, lat, lng, address, opening_hours, updated_at
                index (category, lat, lng)、index (lat, lng)
my_places       id, user_id, name(公司|爸媽家|…), lat, lng, icon, transport(walk|transit|drive), created_at
```

面（公園、醫院是 way / relation）取中心點存成一個點即可。

## 查詢方式

**附近搜尋**：`GET /api/nearby?lat=&lng=&radius=800&cats=超商,公園`
1. D1 用 bounding box 先篩（`lat BETWEEN … AND lng BETWEEN …`，走 (lat, lng) 索引，半徑 800m 大約 ±0.0072 度），
2. Worker 端算 haversine 距離、過濾半徑、依類別分組、每類依距離排序取前 N 筆，
3. 回 `{ counts: {超商: 5, 公園: 2, …}, items: [{category, name, distance_m, walk_min, lat, lng}] }`。
   步行分鐘 = 距離 × 1.3 ÷ 80。

一次查詢讀幾百列（bbox 內的點），每天讀取量不成問題；再用 KV 以「四捨五入到 100m 的座標 + 半徑」當 key 快取 1 天。

**我的地點距離**：房源列表 API 回每間房源到每個 my_place 的直線距離（Worker 端算，my_places 只有幾筆）；篩選列可加「離公司 3 公里內」；比較表（M8）多一列「到公司」。之後要真實通勤時間再接路徑 API，先直線距離。

## 介面

- **房源面板**新增「生活機能」區塊：預設半徑 500m 的各類數量（超商 3 · 超市 1 · 診所 4 · 公園 2 · 廟 1），點某一類展開最近 5 筆與步行分鐘。可切 500m / 1km。
- **地圖右鍵 / 長按任意點**：出現「看附近」，同一個面板但標題是座標或地址（反查 Nominatim）。
- 展開某類時，該類的點畫在地圖上（小圓點 + 名稱，只畫半徑內），並畫一個半徑圈；關閉面板就清掉。
- **我的地點**：設定頁（或篩選列裡的「我的地點」）新增：在地圖上點一下或輸入地址，取名字、挑圖示。地圖常駐顯示這些點（不同形狀的標記），面板顯示「到 公司 2.4 km · 步行 39 分」。
- 篩選列：「離 〔公司▾〕 〔3 km▾〕 內」。

## 分階段

0. **公車路線**（優先）：註冊 TDX → `scripts/fetch_bus.ts` 下載雙北站牌與路線站序 → 三張表 + `/api/nearby/bus` → 面板路線徽章。約半天到一天。591 parser 順手存 `raw_json.traffic`。
1. **PoI 資料**：`scripts/fetch_pois.ts`（Overpass 分類分批抓 → `POST /api/ingest/pois` 覆蓋式更新）+ `pois` 表 + `/api/nearby`。約半天。
2. **面板生活機能區塊 + 地圖畫點**：約半天。
3. **我的地點**：表 + API + 地圖標記 + 面板距離 + 篩選。約半天。
4. 之後：通勤時間（路徑 API）、公園 / 醫院用多邊形算「最近邊界」而不是中心點、把「附近有什麼」餵進 AI 分析（M7）。

## 風險

- OSM 餐飲小店缺漏：介面上標明「資料來源 OpenStreetMap」，別讓使用者以為附近沒吃的。
- Overpass 抓全量一次要幾十分鐘且可能被限速：腳本要能斷點續抓（依類別記進度）。
- 名稱多語：OSM 的 `name` 在台灣多半是中文，缺的時候退回 `name:zh` / `name:en`。
